# 2.1.10 整体绕行、增量搜索修复与恢复交接

本版直接修改本次上传的节点源码包。针对 2026-10-08 122232 日志中四号无人机的长等待：短窗口局部修补无法绕过长隔墙，细网格整体搜索耗时，地图变化又丢失搜索进度；新路线出现后，飞机仍沿旧脱困动作移动，导致接管迟迟不能满足条件。

## 修改逻辑

| 问题 | 本版处理 |
| --- | --- |
| 长隔墙的绕行范围超出短局部修补窗口 | 保留局部修补，同时增加稀疏网格的整体绕行搜索。局部修补连续失败后缩短其预算，为整体绕行留出时间。 |
| 整体细网格搜索扩展大量节点 | 默认使用约 0.54 m 的稀疏搜索间距，仍在原 0.18 m 地图上检查每条边的完整机体扫掠。粗网格找不到窄门时继续细网格与原三维搜索。没有缩小障碍或飞机包络。 |
| 地图更新使未完成搜索反复重启 | 比较当前有界搜索区域中的占据变化，只剪除失效节点及依赖它们的子树；重开受影响的有效邻居和父节点。扫描、剪枝和重开均分配到有界续跑中，未受影响节点保留。 |
| 障碍消失、门口变通，但已耗尽的搜索不再探索 | 障碍移除也会触发边界重开，使已探索一侧能继续穿过新通道。 |
| 没有路线就反复小幅脱困，尤其沿长墙横移 | 在正常输入条件下，净空充足且规划仍在搜索时安全悬停；靠近障碍超过等待窗口后才允许现有认证恢复。缺少可执行路线时，观测空间脱困优先增加净空。 |
| 新路线出现后仍继续旧脱困，逐渐偏离接回范围 | 新路线有经物理碰撞检查的局部连接时先刹停；停稳后面向连接方向获取观测，以零平移等待自由空间、玻璃风险和稳定性检查。认证通过后结束旧恢复。 |
| 旧路径截断段止于硬包络边缘，容易继续逼近墙体 | 仅对已被障碍截断的临时保留段，优先后退到具有运行余量的终点。没有把这一额外余量变成所有窄门的硬膨胀。 |

稀疏搜索、细搜索和局部修补使用相同的未知空间、净空、高度和他机路线软代价。新增搜索仍经过原路径剪枝、平滑、曲率/动力学、路线继承和最新地图提交检查。

增量修复是保留搜索树并修复受影响分支，不是完整 LPA* 或 D* Lite。地图改变后保留代价作为搜索提示，不承诺全局最短路径；候选路径须在最新地图上重新检查才可发布。真正的新目标、起点大幅移动或起点连接受阻，仍可重新建立搜索。

## 配置

在 `config/safe_airfar.yaml` 中新增或调整：

| 参数 | 默认值 | 作用 |
| --- | --- | --- |
| `coarse_detour_enabled` | true | 开启稀疏网格的整体绕行搜索。 |
| `coarse_detour_resolution` | 0.54 m | 搜索间距，按地图分辨率向上取整数倍。碰撞检查分辨率不变。 |
| `coarse_detour_budget_ms` | 65 ms | 单次整体稀疏搜索的目标预算，还受当前剩余规划预算限制；为细搜索保留份额。 |
| `coarse_detour_min_distance` | 6.0 m | 搜索起终点达到此距离且直线受阻时尝试整体稀疏搜索。 |
| `search_snapshot_max_age` | 1.0 s | 实际墙钟下检查未完成搜索是否需要地图修复的间隔，原默认 8 s。不是路线检查周期。 |
| `planning_wait_grace` | 2.0 s | ROS/仿真时间下的短暂规划等待窗口。 |
| `planning_wait_wall_grace` | 6.0 s | 慢仿真时对应等待窗口的实际时间上限；两个窗口任一到期即可结束近障碍宽限。 |
| `operational_clearance` | 0.25 m | 沿用原硬机体包络之外的运行余量，也用于受阻临时路径终点。 |

净空达到 `operational_clearance + 0.05 m` 且规划仍在工作时，允许持续悬停等待，不主动沿墙挪动。明确的跟随卡停和他机死锁仍可越过普通规划等待条件进入原认证恢复。原恢复总距离、次数、冷却、历史轨迹、机间和入口规则继续有效。

真正的新路线局部接回允许的投影误差由 0.25 m 调整为 0.80 m，但实际位置到前方路线的整段连接必须重新通过完整机体、自由空间和玻璃风险检查；这不是减少膨胀。新路线认证检查目标间隔为 0.10 s，稳定窗口为 0.15 s，均使用 ROS/仿真时间。相同旧路线的心跳保留原 0.25 m 接回误差与 0.30 s 稳定窗口，不能立即打断原地尚未移动的恢复。

保持 0.05 s 目标路线检查/刷新周期与 1.80 m/s 最大水平速度。当前 CPU、DDS、地图和仿真实时因子仍决定实际响应速度；本次没有修改 PX4 PID。安全悬停可能持续到找到可执行路线，地图本身不可达时不能保证继续前进。

## 替换与编译

先 Ctrl-C 结束旧规划 launch。将压缩包内完整 `fire_scout_planning_safe` 文件夹替换到 `~/fire_scout_ws/src/`。旧源码备份放到 `src/` 外，避免发现同名包。自定义起点、展开间距等按项合并，不要用旧 YAML 整体覆盖本版配置。

```bash
cd ~/fire_scout_ws
source /opt/ros/humble/setup.bash
colcon build --packages-select fire_scout_planning_safe --cmake-clean-cache \
  --cmake-args -DCMAKE_BUILD_TYPE=Release -DFIRE_SCOUT_CORE_ONLY=OFF
source install/setup.bash
export ROS_DOMAIN_ID=0
```

也可以使用包内安装脚本。编译后重新启动节点；`source` 不会替换已经运行的旧进程。

PX4、Gazebo、传感器和定位桥接沿用原流程。四机规划示例：

```bash
ros2 launch fire_scout_planning_safe multi_racer_navigation.launch.py \
  scout_count:=4 use_sim_time:=true start_mapper:=true \
  racer_enabled:=false auto_arm:=true
```

三机使用 `scout_count:=3`。默认起点仍为 `scout1=(-12.5,-9,0.2)`、`scout2=(-12.5,-1,0.2)`、`scout3=(-12.5,8,0.2)`、`scout4=(-12.5,17,0.2)`，应与实际 `PX4_GZ_MODEL_POSE` 对应；自定义时设置 `scout_origins`。多机展开、目标点和 Racer 接口沿用现有包。

```bash
ros2 param get /scout1/safe_airfar_like_planner runtime_version
ros2 param get /scout1/safe_airfar_path_follower runtime_version
```

分别应为 `2.1.10-incremental-detour` 和 `2.1.10-safe-planning-handoff`。其他未修改模块可以继续显示自己的历史标识。

## 诊断与轻量日志

已有轻量日志自动记录新增的状态和字段，不需要录制完整点云：

```bash
ros2 run fire_scout_planning_safe collect_fire_scout_logs.sh \
  --duration 900 --scouts 4 --max-mb 24
```

900 s 是实际录制时间，24 MiB 是事件文件上限。达到上限会正常结束并打包，归档还含少量配置和系统信息。三机改为 `--scouts 3`。

| 状态或字段 | 含义 |
| --- | --- |
| `COARSE_DETOUR` | 稀疏搜索生成整体绕行候选，已通过细地图几何检查。 |
| `guide_expansions` | 当次稀疏搜索工作量。 |
| `search_repair_events` / `search_repair_removed` | 本规划器及子搜索累计修复事件、删除的依赖节点数。 |
| `search_repair_preserved` | 完成修复时保留节点数的峰值，用于确认未把整个搜索清空。 |
| `search_repair_pending` | 搜索仍有待处理或未完成的地图修复。 |
| `PLANNING_WAIT_HOLD` | 无可执行路线，正在等待规划，未主动启动新的局部脱困。 |
| `planning_wait_reason` / `planning_wait_seconds` | 等待原因与本轮累计 ROS 时间；普通搜索心跳不重置计时。 |
| `planner_searching` | 规划器报告仍在搜索/等待重试，仅作诊断与等待建议，不授予路线执行权限。 |
| `RECOVERY_HANDOFF_BRAKE` | 新路线已有物理连接，先消除旧恢复动作的实测速度。 |
| `RECOVERY_HANDOFF_OBSERVE` | 零平移面向接回方向等待观测认证。 |

结合地图源时间、节点状态、仿真实时因子、机间约束和实际速度看等待原因。不要仅凭 RViz 出现一条线就判断跟随器应立刻执行。

## 验证范围

36 项便携回归检查：25 项 C++ 核心测试与 11 项 Python/生产方法片段/launch 测试。新增或扩展覆盖长隔墙绕行、窄门细搜索回退、障碍新增与移除、保留搜索分支、临时路径终点余量、搜索建议不能授予执行权限、等待窗口/时钟回退、实际 NAV 等待分支，以及先制动再观测的新路线接管。

同一合成长墙场景、相同机体包络和成本参数下，包含并行继续细搜索的总扩展次数由 4318 降为 1425，约减少 67%。这是可复现的搜索工作量比较，不代表实际多机飞行耗时降低 67%。测试也确认稀疏网格无法穿过的偏置窄门能由细网格找到。

结果与环境限制见 `v2_1_10_validation.json`。当前执行环境没有 ROS 2、colcon、CMake、PX4/Gazebo，未进行完整 ROS 节点构建、DDS/TF 联调、最新地图原始数据重放或多机飞行；需要在原工作空间编译后复测同一目标与四号绕墙场景。
